# Identity and Driver Data Ownership

Status: Implemented
Last updated: 2026-09-24

PostgreSQL is the durable authority. Identity module code is the sole writer for `identity.*`; Driver module code is the sole writer for `driver.*`. Future modules consume contracts or events rather than writing these tables directly.

## Identity schema

| Table                       | Owner    | Purpose                                                                                |
| --------------------------- | -------- | -------------------------------------------------------------------------------------- |
| `identity.users`            | Identity | Canonical user identity, normalized email, lifecycle status, and authentication epoch. |
| `identity.roles`            | Identity | Fixed role catalogue: Customer, Driver, Operator.                                      |
| `identity.user_roles`       | Identity | Authorized role assignments.                                                           |
| `identity.credentials`      | Identity | Current Argon2id password hash for a user.                                             |
| `identity.refresh_sessions` | Identity | Digested opaque refresh tokens, lifecycle, expiry, and rotation family.                |
| `identity.command_receipts` | Identity | Idempotent registration outcome keyed by operation, subject, and client key.           |

`identity.refresh_sessions` permits one active session per token family. Refresh is a database transaction with row locking so concurrent rotation and replay resolution observe one durable order.

## Driver schema

| Table                    | Owner  | Purpose                                                                             |
| ------------------------ | ------ | ----------------------------------------------------------------------------------- |
| `driver.driver_profiles` | Driver | Review status and contact data for a user with the Driver role.                     |
| `driver.vehicles`        | Driver | A driver-owned vehicle, its review state, selected state, and retirement timestamp. |

Both profile and vehicle begin `PENDING`. An approved profile plus one approved selected vehicle is necessary, but not sufficient, for later dispatch: current work state and latest-location freshness remain separate dispatch concerns.

## Migration rules

Migrations `0002-identity-auth.sql` and `0003-driver-profile-and-vehicle.sql` add only new schemas, tables, constraints, indexes, and update triggers. They do not seed credentials or personal data. UUIDs are generated by application code, keeping database initialization deterministic and avoiding hidden demo identities.
